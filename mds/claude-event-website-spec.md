# Техническое задание для Claude Code: сайт организатора праздников

## 1. Задача и контекст

Создай полноценный адаптивный сайт организатора праздников и встроенную административную панель. Владелица сайта организует разные мероприятия: научные шоу, танцевальные программы и другие праздники. Точный перечень услуг будет добавляться позднее через админку.

Нужна собственная компактная CMS с логикой типов записей, похожей на WordPress: обычные страницы, иерархические услуги, статьи блога и категории статей. Не устанавливай WordPress. Публичная часть, админка и серверная логика работают в одном приложении Next.js с PostgreSQL, без отдельного Django-бэкенда.

Пользователь предоставит изображения-референсы и реквизиты уже созданной локальной базы. В этой задаче требуется реализовать приложение, а не ограничиться планом или статическим макетом. Рутинные технические решения принимай самостоятельно в рамках ТЗ. Недостающие название бренда, услуги и тексты не должны блокировать разработку: используй редактируемые, явно демонстрационные данные.

## 2. Обязательный стек и запуск

Из корня проекта выполни именно:

```bash
npx create-next-app@latest frontend --yes
```

Имя каталога — `frontend` в нижнем регистре, как в команде. Всё приложение, включая серверную часть и админку, находится в нём. Не создавай вложенный `frontend/frontend` или параллельный `Frontend`.

Требования:

- Последняя стабильная версия Next.js на момент начала реализации, App Router, TypeScript со строгой проверкой и Tailwind CSS.
- npm и зафиксированный `package-lock.json`.
- PostgreSQL; для схемы, запросов и миграций использовать Prisma ORM в актуальной совместимой версии.
- Server Components по умолчанию; Client Components только там, где нужна интерактивность.
- Server Actions для внутренних форм и изменений; Route Handlers для внешних HTTP-интерфейсов, загрузок и необходимых интеграций. Не создавать REST API для каждого чтения данных без необходимости.
- Zod или эквивалентная общая схема валидации на сервере; клиентская проверка дополняет серверную.
- Поддерживаемая библиотека аутентификации, совместимая с установленным Next.js. Не разрабатывать собственную криптографию или протокол сессий.

До установки проверь требования актуальных версий к Node.js. `--yes` может использовать сохранённые настройки: после генерации убедись, что включены TypeScript, Tailwind и App Router. При необходимости исправь конфигурацию без повторного создания проекта. Зафиксируй фактические версии и нужную версию Node.js в README. Используй документацию установленной версии, а не устаревшие примеры API, кеширования или настройки Tailwind.

## 3. Подключение к существующей базе

Пользователь сам создаёт базу в pgAdmin и предоставляет host, port, database, username, password. Не создавай другую базу вместо предоставленной и не заменяй PostgreSQL на SQLite или облачный сервис.

- Собери серверную `DATABASE_URL`; корректно кодируй специальные символы реквизитов.
- Секреты храни в исключённом из Git env-файле. Подготовь `.env.example` только с заглушками.
- Учитывай, что приложение и Prisma CLI должны получать одинаковую конфигурацию окружения; документируй способ загрузки env.
- Не используй `NEXT_PUBLIC_` для доступа к базе, секретов сессий и серверных ключей. Не выводи реквизиты в логи.
- До первой миграции проверь подключение и существующие таблицы. Пустая предоставленная база предназначена для схемы приложения; существующие данные не удалять и не перезаписывать.
- Схему вести через версионированные миграции. Не применять reset/drop или автоматическую потерю данных. Если dev-миграциям нужна shadow database, не предполагай наличие права CREATE DATABASE: используй подготовленную миграцию и подходящий недеструктивный workflow, опиши его.
- Подключение к БД выполняется только на сервере. Предусмотри корректное переиспользование клиента при hot reload и ограничение подключений.

## 4. Модель контента

Создай отдельные типизированные таблицы `Page`, `Service`, `Post`, `Category`. Общие поля и UI можно переиспользовать, но не своди всю бизнес-модель к одной бесструктурной JSON-таблице.

### 4.1. Общие поля публикаций

Для Page, Service и Post:

- `id`: UUID, `title`, `slug`, `status`: DRAFT / PUBLISHED / ARCHIVED.
- `excerpt`: необязательный краткий текст; `content`: структурированный JSON редактора.
- `coverMediaId`: необязательная ссылка на медиабиблиотеку.
- `seoTitle`, `seoDescription`, `ogMediaId`, `noIndex`.
- `createdAt`, `updatedAt`, `publishedAt`, `createdById`, `updatedById`.

Обязательность title/slug проверять перед публикацией. В первой версии публикация немедленная; не добавлять расписание публикаций без фонового механизма. Черновики и архив не доступны публично, в sitemap, поисковых списках и связанных блоках. Все даты сохранять с учётом часового пояса; бизнес-отображение по умолчанию Europe/Moscow, настройка редактируется.

### 4.2. Обычные страницы — Page

Примеры: главная, «О нас», «Контакты», информационная страница.

Дополнительные поля: `templateKey`, `templateData` (JSON с проверяемой схемой), `isHome`.

- Реестр шаблонов в коде: `home`, `default`, `about`, `contacts`.
- В админке шаблон выбирается из реестра; нельзя вводить произвольный путь к компоненту или исполняемый код.
- У каждого шаблона свои типизированные данные и форма редактирования: hero, текст, галерея, CTA, контакты и т. п.
- Контент, заголовки, изображения и порядок поддерживаемых секций редактируются через админку. Новый вид секции/шаблона добавляет разработчик.
- Только одна главная страница: обеспечить ограничением БД и транзакцией назначения. Нельзя случайно снять с публикации единственную главную без назначения замены.
- В этой версии обычные страницы имеют один сегмент URL; иерархия обязательна только для услуг.

### 4.3. Услуги — Service

Дополнительные поля: `parentId` nullable, `sortOrder`, `templateKey`, `templateData`, `isFeatured`; необязательные `priceFrom` (Decimal), `currency`, `durationMinutes`. Отсутствие цены выводить как «По запросу», не как ноль.

Услуга может быть самостоятельной (`parentId = null`), родительской с собственным содержимым, дочерней и одновременно родительской для следующего уровня. Модель поддерживает произвольную глубину, интерфейс должен отображать её понятно.

- Self-relation `parentId → Service.id`; удаление родителя не каскадирует удаление детей.
- Запрет собственного id и любого потомка в качестве родителя; цикл проверять на сервере. Изменение дерева делать транзакционно с защитой от конкурентных изменений, способных создать цикл.
- Нельзя публиковать дочернюю услугу при неопубликованном предке. Снятие родителя с публикации при опубликованных потомках блокируется с понятным объяснением.
- Удаление родителя с детьми блокируется: сначала перенести или удалить детей. Архивирование подчиняется тому же правилу видимости.
- Сортировка по `sortOrder`, затем стабильному дополнительному полю.
- Для первой версии `slug` услуги уникален глобально внутри Service, даже если родители разные. Это намеренное упрощение; одинаковые slugs у разных типов записей допустимы благодаря URL-префиксам.
- Шаблоны `service-default` и `service-group`: родительская страница показывает собственное описание и опубликованные дочерние услуги. Не делай тип услуги жёстким enum «наука/танцы».

Пример дерева только для демонстрационного seed: «Научные шоу» → «Тесла-шоу», «Крио-шоу»; отдельно «Танцевальные программы». Новые направления должны добавляться без изменения схемы и кода.

### 4.4. Статьи — Post, категории — Category

- Post содержит автора (`authorId`), обложку, анонс, основной текст и связь many-to-many с Category через `PostCategory`.
- Category: `id`, `name`, уникальный `slug`, `description`, SEO-поля, timestamps.
- Категории в первой версии плоские. Одна статья может принадлежать нескольким категориям; перед публикацией требуется минимум одна.
- `PostCategory` имеет составной уникальный ключ по postId/categoryId.
- Удаление используемой категории блокировать до переназначения статей; статьи не удалять каскадно.
- В блоге — пагинация и фильтрация по категории. Сортировка опубликованных статей по publishedAt, затем id.

### 4.5. Остальные сущности

| Сущность | Назначение и основные поля |
| --- | --- |
| User и таблицы сессий | Пользователь админки, email с уникальностью без учёта регистра, имя, роль ADMIN/EDITOR, признак активности; поля аутентификации по выбранной библиотеке |
| Media | storageKey, исходное имя, MIME, размер, width/height, alt, createdAt; файлы хранятся отдельно от PostgreSQL |
| Inquiry | Имя, телефон, email необязательно, сообщение, serviceId необязательно, желаемая дата необязательно, статус NEW/IN_PROGRESS/DONE/SPAM, источник страницы, createdAt |
| SiteSettings | Название, описание, логотип, контакты, социальные ссылки, часовой пояс, общие SEO-значения |
| Menu / MenuItem | Меню header/footer, подпись, порядок, ссылка на сущность либо внешний URL, необязательный parentId для вложенности |
| Redirect | Уникальный sourcePath, targetPath, code=301; история опубликованных URL |

Для ссылок меню сохранять id сущности и строить актуальный URL, а не копировать устаревающий slug. Проверять допустимые схемы внешних ссылок. Добавить внешние ключи, ограничения и индексы для slug, parentId/sortOrder, status/publishedAt и связующих таблиц. Обязательные правила обеспечивать БД там, где это возможно, остальное — серверной валидацией и транзакциями.

## 5. URL и маршруты

| URL | Содержание |
| --- | --- |
| `/` | Главная Page с isHome=true |
| `/[slug]` | Обычная опубликованная Page |
| `/services` | Каталог верхнеуровневых услуг |
| `/services/[...slug]` | Услуга по полному пути родителей |
| `/blog` | Статьи с пагинацией |
| `/blog/[slug]` | Статья |
| `/blog/category/[slug]` | Статьи категории |
| `/admin/login` | Вход |
| `/admin/...` | Защищённая админка |

Пример: `/services/science/tesla`. Иерархия URL должна точно совпадать с деревом; нельзя отдавать услугу по неверному набору предков только потому, что последний slug найден. Хлебные крошки строятся из данных.

Зарезервировать для Page системные сегменты `admin`, `api`, `services`, `blog` и реальные технические маршруты приложения. Главная не должна открываться дубликатом по своему slug: перенаправлять на `/`. Slug нормализовать в нижний регистр, применять единое правило латинской транслитерации, разрешить ручное редактирование, валидировать формат и уникальность на сервере и в БД.

При смене slug опубликованного контента сохранять старый адрес как 301. При перемещении услуги или изменении slug родителя обновить пути всей ветви и редиректы потомков в одной согласованной операции. Не допускать конфликтов с действующими URL, циклов редиректов и длинных цепочек: старые адреса должны вести на конечный актуальный. Архивные и черновые записи не раскрывать через редиректы.

Несуществующее и неопубликованное содержимое — 404. Предпросмотр черновика доступен только авторизованному редактору, не кешируется публично и содержит noindex.

## 6. Организация кода

Компоненты обязательно находятся в каталоге `Components` с заглавной C, разделённом по доменным сущностям. Не складывать все компоненты в одну папку. Использовать единый регистр путей во всех импортах, учитывая Linux.

Предпочтительно расположить `app`, `Components`, `lib`, `server` в корне `frontend`. Если генератор создал `src`, привести к этому соглашению и настроить alias `@/*`.

| Каталог внутри frontend | Ответственность |
| --- | --- |
| `app/(public)` | Публичные маршруты и layout |
| `app/(admin)/admin` | Вход и административные маршруты; защищённые страницы выделить во вложенную route group |
| `app/api` | Необходимые Route Handlers |
| `Components/ui` | Переиспользуемые кнопки, поля, диалоги, таблицы |
| `Components/layout` | Header, Footer, навигация, административная оболочка |
| `Components/pages` | Шаблоны и секции обычных страниц |
| `Components/services` | Карточки, дерево, шаблоны и формы услуг |
| `Components/blog` | Карточки и представления статей |
| `Components/categories` | Выбор и управление категориями |
| `Components/media` | Медиабиблиотека и выбор изображений |
| `Components/inquiries` | Публичная форма и управление заявками |
| `Components/auth` | Формы входа и элементы управления сессией |
| `Components/settings` | Формы общих настроек и меню |
| `Components/editor` | Редактор содержимого и рендерер |
| `server/<domain>` | Запросы, изменения, проверки доступа и бизнес-правила соответствующей сущности |
| `lib` | Клиент БД, auth-конфигурация, общие утилиты и схемы |
| `prisma` | Схема, миграции, seed |

Страницы маршрутов должны собирать UI, а не содержать всю бизнес-логику. Серверные модули обозначить server-only; не импортировать ORM и секреты в клиентский граф. Не вызывай собственный HTTP API из Server Components для обычного чтения БД. Не создавай чрезмерную абстракцию ради будущих функций.

## 7. Административная панель

Сделай работающую русскоязычную админку, пригодную для владелицы без навыков программирования.

- Разделы: страницы, услуги, блог, категории, медиа, заявки, меню, настройки, пользователи.
- Списки с поиском, фильтрами статуса, пагинацией, понятными пустыми состояниями.
- Создание, редактирование, публикация, снятие с публикации, архивирование, удаление с подтверждением и учётом связей.
- Для услуг — дерево, выбор родителя, порядок, переход к дочерним записям.
- Для страниц — выбор шаблона, форма полей выбранного шаблона и предпросмотр.
- Для статей — выбор категорий и автора, обложка, анонс, SEO.
- Редактор форматированного текста: абзацы, H2/H3, списки, ссылки, изображения. Хранение в документированном JSON-формате; безопасный рендеринг без выполнения HTML/JS из базы.
- Переключение шаблона не должно молча терять заполненные данные: сохранять совместимые поля, предупреждать о несовместимых.
- Защита от случайного ухода с несохранёнными изменениями; ошибки полей и сохранения показывать рядом с формой. Не показывать успех до подтверждения БД.
- После изменения контента публичные страницы, связанные списки, меню, хлебные крошки и SEO обновляются без ручного перезапуска.

ADMIN управляет всем, включая пользователей, настройки и заявки. EDITOR управляет страницами, услугами, статьями, категориями и медиа, но не пользователями, реквизитами, настройками и персональными данными заявок. Проверять роль в каждом серверном чтении чувствительных данных и каждой операции изменения. Защиты только layout или скрытой кнопки недостаточно.

Создание первого ADMIN — отдельная документированная локальная команда с безопасным вводом пароля, без пароля по умолчанию в seed. Публичной регистрации нет. Неактивный пользователь не может войти; отключение пользователя должно прекращать доступ действующей сессии.

## 8. Дизайн и публичная часть

Пользователь передаст визуальные референсы. Проанализируй их композицию, типографику, цвета, отступы, кнопки и подачу изображений и реализуй дизайн настоящими компонентами. Не вставляй скриншот целиком вместо страницы.

Научный персонаж и образцы научных шоу — материалы одного направления, а не ограничение всего бизнеса. Не закрепляй «ВАУ! НАУКА» как окончательное название бренда без подтверждения. Главная представляет организатора праздников и все направления; научное направление может иметь собственную выразительную страницу. Название, фотографии, услуги, меню и тексты редактируются из CMS.

Первая версия публичной части: главная, каталог услуг, услуги обоих шаблонов, «О нас», «Контакты», блог, статья, категория, форма заявки. Главная: hero, блок направлений, информация об организаторе, поддерживаемая галерея, CTA. Не выдумывать реальные отзывы, награды, число клиентов, стоимость и контакты; демонстрационные данные обозначить и сделать заменяемыми.

Адаптация от 360 px до широкого desktop, отсутствие горизонтального скролла, понятное мобильное меню, видимый focus, доступность клавиатурой и подписанные поля. Анимация умеренная, учитывает prefers-reduced-motion. Изображения оптимизировать с известными размерами; видео не блокирует загрузку и не воспроизводит звук автоматически. H1 один на страницу; содержательная структура заголовков.

## 9. Медиа и заявки

Медиа: первая реализация для локального сервера/VPS хранит файлы в отдельном постоянном каталоге, настраиваемом через env; метаданные и ключи — в БД. Не полагаться на запись в build-каталог или ephemeral filesystem. Сделать небольшой storage-адаптер для будущей замены на объектное хранилище, без обязательной интеграции с облаком сейчас. Настроить выдачу/оптимизацию файлов и описать резервное копирование файлов вместе с БД.

Загрузки доступны только авторизованным ролям: allowlist форматов изображений, проверка MIME/содержимого, лимит размера, безопасное генерируемое имя, защита от обхода пути. SVG не принимать без безопасной обработки. Не удалять используемый файл молча; показать связанные записи. Alt редактируется, декоративные изображения могут иметь пустой alt.

Публичная заявка содержит имя, телефон, необязательные email, дату и сообщение, контекст выбранной услуги. Валидировать на сервере, ограничить длины, добавить honeypot и ограничение частоты, работающее в выбранном окружении. Сначала сохранить заявку в PostgreSQL, затем показывать успех. Уведомления — необязательная интеграция; без предоставленных реквизитов достаточно надёжного сохранения и списка в админке. Сбой уведомления не отменяет сохранённую заявку. Предусмотреть требуемую форму согласия и ссылку на редактируемую политику; не выдавать демонстрационный юридический текст за согласованный документ.

## 10. SEO, кеширование и безопасность

- Metadata API: title, description, canonical, Open Graph на основе записи и настроек.
- Sitemap только для опубликованных canonical URL; robots исключает admin и технические маршруты. Robots не заменяет авторизацию.
- BASE_URL задаётся окружением; URL не зашиты на localhost.
- Выбрать и описать стратегию кеширования актуального Next.js. После мутации инвалидировать зависимые страницы и списки, включая старые и новые пути ветвей; черновики, сессии и заявки не попадут в общий кеш.
- На публичном серверном рендере не зависеть от client-only загрузки основного текста.
- Все мутации и защищённые запросы проверяют пользователя, роль и входные данные на сервере; применять защиты выбранной auth-библиотеки, безопасные cookies и ограничение попыток входа.
- Не принимать raw SQL, исполняемый код, произвольный template path или небезопасную разметку от CMS.
- Не раскрывать stack trace, env и персональные данные в публичных ошибках/логах. Для админки и БД использовать Node runtime с учётом драйвера, не Edge по умолчанию.

## 11. Начальные данные и границы первой версии

Подготовить идемпотентный opt-in seed для демонстрации: главная, о нас, контакты, один родитель услуг с двумя дочерними, одна самостоятельная услуга, две категории, две статьи. Seed не должен перезаписывать правки владельца при повторном запуске, создавать администратора с известным паролем или запускаться автоматически в production.

Не входят в текущую версию: расписание исполнителей, склад реквизита, бухгалтерия, онлайн-оплата, личный кабинет клиента, мультиязычность, универсальный drag-and-drop конструктор страниц и полноценное версионирование редакций. Архитектура не должна препятствовать их добавлению, но сейчас реализуй именно CMS и заявки.

## 12. Порядок реализации и проверка

1. Проверить окружение и материалы, создать Next.js указанной командой, установить совместимые зависимости.
2. Подключить предоставленную БД, подготовить схему, ограничения и миграции.
3. Реализовать вход, роли, создание первого администратора.
4. Реализовать CMS: страницы и шаблоны, дерево услуг, блог/категории, медиа, настройки и меню.
5. Собрать публичные страницы по референсам с данными из БД.
6. Реализовать заявки, SEO, предпросмотр, редиректы и обновление кеша.
7. Проверить ключевые сценарии, адаптивность и production build; написать README.

Не останавливайся после статического дизайна. Если реквизиты БД отсутствуют, подготовь код, миграции и env-пример, затем точно укажи недостающие параметры. Не утверждай, что интеграция с БД проверена, пока реальное подключение не выполнено.

Минимальные содержательные автоматические проверки:

- Прямой вызов защищённой операции без сессии или с недостаточной ролью отклоняется.
- Цикл дерева услуг запрещён, перенос ветви сохраняет целостность и адреса.
- Неопубликованная запись и её данные не доступны публично.
- Перенос/переименование родителя создаёт корректные редиректы потомков; неверный путь возвращает 404.
- Нарушение уникальности slug и конфликт системного URL отклоняются.
- Статья корректно работает с несколькими категориями; запрет удаления используемой категории соблюдается.
- Валидная заявка сохраняется, невалидная отклоняется.

Ручной сквозной сценарий: войти → создать родительскую и дочернюю услуги → заполнить содержимое → опубликовать → открыть публичные URL → изменить slug родителя → проверить новый URL и 301 старого → создать статью с категориями → отправить заявку → увидеть её в админке. Проверить public и admin на мобильной ширине. Выполнить lint, TypeScript check и production build; не скрывать ошибки отключением проверок.

## 13. Критерии готовности и передача

Работа завершена, когда:

- Приложение запускается из `frontend`, использует App Router, Tailwind и предоставленную PostgreSQL.
- Все указанные типы контента реально сохраняются и редактируются через защищённую админку.
- Иерархия услуг, публикация, шаблоны, категории и URL работают по правилам ТЗ.
- Владелица может добавить новое направление без правки кода.
- Публичные страницы визуально соответствуют направлению референсов, адаптивны и используют контент CMS.
- Заявки сохраняются, роли проверяются сервером, секретов нет в репозитории.
- Есть миграции, `.env.example`, безопасная команда создания ADMIN, opt-in seed и README.
- В README описаны установка, env, миграции без потери данных, запуск, production build/start, хранение медиа, backup, работа шаблонов, роли и фактические версии.

В итоговом отчёте кратко перечисли реализованное, команды запуска, проверенные сценарии и оставшиеся ограничения. Отдельно отметь любые проверки, которые не удалось выполнить. Не публикуй сайт и не меняй production-инфраструктуру: результат этой задачи — локально работающий проект.
