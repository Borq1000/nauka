## 2. Окружение (проверено фактически, не предположено)

| Параметр | Значение |
|---|---|
| Node.js | v22.16.0 |
| npm | 10.9.2 |
| PostgreSQL | 16.9, `localhost:5432`, слушает (процессы `PostgreSQL\16\bin\postgres.exe`) |
| База | `events`, UTF8, **таблиц нет** |
| Роль | `postgres`, `rolsuper = t`, `rolcreatedb = t` |

**Следствие для миграций.** Право `CREATEDB` подтверждено, поэтому
`prisma migrate dev` сможет самостоятельно поднимать shadow database.
Обходной workflow через `migrate diff` не нужен. В README описывается, что на
VPS приложение должно ходить под ролью без `SUPERUSER`/`CREATEDB`, а миграции
применяться командой `migrate deploy`.

**Замечание по службе Windows.** `Get-Service postgresql-x64-16` сообщает
`Stopped`, при этом сервер работает и принимает подключения. Служба запущена в
обход Service Control Manager. Это фиксируется в README, чтобы диагностика
«база не отвечает» не начиналась с ложного следа.

## 4. Хранение и рендеринг контента

**Решение:** контент хранится деревом типизированных узлов в колонке `jsonb`;
публичный рендерер сопоставляет тип узла React-компоненту.

**Обоснование.** Санитизация HTML работает как чёрный список («разрешено всё,
кроме известного плохого») — пропущенный вектор означает XSS у всех
посетителей. Рендерер по дереву работает как белый список («не рендерится
ничего, кроме известного хорошего») — неизвестный тип узла не имеет ветки в
`switch` и просто не отображается. Ошибка деградирует в «блок не показался»
вместо «выполнился чужой код».

Реализация опирается на пять правил:

1. **Валидация на записи.** Zod-схема документа применяется в Server Action
   **до** сохранения. Невалидный документ в базу не попадает. Whitelist в
   рендерере остаётся вторым рубежом на случай данных в обход приложения.
2. **Рендер React-компонентами.** Функция TipTap `generateHTML` **не
   используется** — она вернула бы строку HTML, которую пришлось бы вставлять
   через `dangerouslySetInnerHTML`. В проекте не должно быть ни одного
   вызова `dangerouslySetInnerHTML`; правило закрепляется ESLint-правилом
   `react/no-danger`.
3. **Изображения по `mediaId`, не по URL.** URL строится при рендере. Смена
   хранилища или структуры каталогов не ломает накопленный контент. Тот же
   принцип ТЗ уже требует для пунктов меню (п. 4.5).
4. **Версионирование формата.** Конверт `{ type: "doc", version: 1, content: [] }`
   делает будущую миграцию формата обычной задачей вместо угадывания.
5. **Тип колонки `jsonb`.** Prisma-тип `Json` на PostgreSQL создаёт `jsonb`.
   Это позволяет запросом найти записи, ссылающиеся на конкретное изображение,
   и выполнить требование ТЗ п. 9 «не удалять используемый файл молча» не
   только для обложек, но и для картинок внутри текста.

**Допустимые узлы** (ровно перечень ТЗ п. 7): `paragraph`, `heading`
(только `level: 2 | 3`), `bulletList`, `orderedList`, `listItem`, `text`,
`image`, марки `bold`, `italic`, `link`.

H1 в редакторе недоступен **по схеме**: `level` типизирован как `2 | 3`.
Единственный H1 на странице рисует шаблон. Требование ТЗ п. 8 «один H1 на
страницу» обеспечивается типом, а не дисциплиной редактора.

**Ссылки.** Схема URL проверяется по allowlist: `http`, `https`, `mailto`,
`tel` и относительные пути. `javascript:` и `data:` отклоняются на записи.

**Выбор TipTap, а не Lexical.** Обе библиотеки MIT. Решающий довод — Lexical
находится в версии `0.50.0`, мажорного релиза не было; ломающие изменения в
формате хранения контента для долгоживущего проекта неприемлемы. TipTap 3.31.3
построен на ProseMirror с более чем десятилетней историей в проде, а нужный
набор узлов целиком покрывается бесплатным `starter-kit` — расширения Pro не
требуются. TipTap используется **только как редактор в админке**: формат
хранения — обычный ProseMirror JSON, публичный рендерер написан вручную и от
TipTap не зависит. Замена редактора в будущем затронет одну форму админки.

## 5. Аутентификация

**Решение:** better-auth 1.7.4 с Prisma-адаптером, сессии в базе.

**Обоснование.** ТЗ п. 7 требует: «отключение пользователя должно прекращать
доступ действующей сессии». Это исключает JWT-сессии — подписанный токен нельзя
отозвать, он действует до истечения срока. Нужны сессии в БД, проверяемые на
каждом запросе.

Рассмотренные альтернативы:

- **Auth.js / next-auth v5** — состояние `5.0.0-beta.32`, beta. Стабильная
  ветка `4.24.15` плохо сочетается с App Router и Server Actions.
- **Собственная реализация** — прямо запрещена ТЗ п. 2.

better-auth даёт из коробки: email+password, сессии в БД, отзыв сессий,
ограничение попыток входа (требование ТЗ п. 10), безопасные cookies.

**Проверка активности.** Сессия считается действительной только если
`user.isActive = true` на момент запроса. Проверка выполняется при каждой
загрузке сессии, а не только при входе.

**Создание первого ADMIN** — отдельная CLI-команда `npm run create-admin` с
скрытым вводом пароля через `readline` без эха. Пароля по умолчанию в seed нет.
Публичной регистрации нет.

## 6. Инварианты, обеспеченные базой данных

Требования ТЗ, где проверка только в коде создаёт гонку.

### 6.1. Единственная главная страница

```sql
CREATE UNIQUE INDEX "Page_isHome_unique" ON "Page" ("isHome") WHERE "isHome" = true;
```

Проверка «нет ли уже главной?» в коде гоночная: два одновременных сохранения
пройдут её оба. Частичный уникальный индекс делает два значения `true`
физически невозможными. Назначение новой главной — одна транзакция: снять флаг
со старой, поставить новой.

### 6.2. Дерево услуг без циклов

Обход предков — рекурсивным CTE внутри транзакции с `SELECT … FOR UPDATE` на
затронутых узлах. Без блокировки две параллельные операции перемещения могут
замкнуть ветку в кольцо, после чего рекурсивный запрос уходит в бесконечность.

Запрещены: собственный `id` в качестве родителя, любой потомок в качестве
родителя.

### 6.3. Материализованный путь

Поле `Service.path` (`science/tesla`) с уникальным индексом.

ТЗ п. 5 требует отдавать услугу только при точном совпадении цепочки предков.
С `path` это один поиск по индексу вместо рекурсивного подъёма на каждый запрос.
При смене slug родителя одна транзакция пересчитывает `path` всей ветви и
создаёт `Redirect` на каждый старый адрес.

### 6.4. Редиректы без цепочек и циклов

**Инвариант:** `targetPath` никогда не является чьим-либо `sourcePath`.

При создании `A → B`:
- если существует `B → C` — записывается сразу `A → C`;
- все существующие `X → A` переписываются на `X → B`.

Редирект не создаётся, если целевой путь принадлежит черновику или архиву
(ТЗ п. 5: «архивные и черновые записи не раскрывать через редиректы»).

### 6.5. Прочие ограничения уровня БД

- Уникальность `slug` внутри каждого типа записей.
- Составной уникальный ключ `PostCategory(postId, categoryId)`.
- `ON DELETE RESTRICT` для родителя услуги, автора статьи, используемой
  категории и используемого медиафайла.
- Индексы: `(status, publishedAt)`, `(parentId, sortOrder)`, `slug`, `path`.
- Email пользователя уникален без учёта регистра: значение нормализуется в
  нижний регистр при записи, уникальность обеспечивается обычным уникальным
  индексом по колонке. Расширение `citext` не используется — оно требует
  `CREATE EXTENSION` (право, которого на VPS может не быть) и в Prisma
  выражается только через `Unsupported`, что лишает колонку типизации.

## 7. Авторизация

Проверка роли выполняется **внутри функций** `server/<domain>` — в каждом чтении
чувствительных данных и каждой мутации.

**Обоснование.** ТЗ п. 7 прямо указывает, что защиты layout недостаточно.
Причина техническая: Server Action публикуется как собственный HTTP-endpoint и
вызывается напрямую, минуя любой layout и любую скрытую кнопку.

| Роль | Доступ |
|---|---|
| ADMIN | всё, включая пользователей, настройки и персональные данные заявок |
| EDITOR | страницы, услуги, статьи, категории, медиа. **Нет** доступа к пользователям, настройкам и персональным данным заявок |

## 8. Медиа

- Файлы — в каталог из env `MEDIA_ROOT`, расположенный **вне** `frontend/`,
  чтобы пересборка его не затирала. Метаданные — в таблицу `Media`.
- Интерфейс `StorageAdapter` (`put` / `get` / `delete`), первая реализация —
  локальная файловая система. Замена на S3 не затрагивает остальной код.
- Отдача через Route Handler с нормализацией пути и защитой от обхода каталога.
- Загрузка: только авторизованным ролям, allowlist форматов
  (`jpeg`, `png`, `webp`, `avif`), проверка реального MIME по содержимому, лимит
  размера, генерируемое имя файла. SVG не принимается.
- Удаление используемого файла блокируется с перечнем связанных записей.
  Использование ищется и в обложках, и внутри `jsonb`-контента.

## 9. Заявки

- Сохранение в PostgreSQL **до** показа успеха (ТЗ п. 9).
- Валидация на сервере: длины полей, формат телефона, honeypot-поле.
- Ограничение частоты по IP — в таблице БД, а не в памяти процесса: память не
  переживает перезапуск и не работает при нескольких инстансах.
- Чекбокс согласия обязателен, ссылка на редактируемую из CMS страницу политики.
  Демонстрационный текст политики помечается как демонстрационный.

## 10. Кеширование

| Что | Стратегия |
|---|---|
| Публичные страницы | статическая генерация с тегами по сущности |
| После мутации | точечная инвалидация: старый путь, новый путь, связанные списки, меню, хлебные крошки, sitemap |
| `/admin/**` | `no-store` |
| Предпросмотр черновика | `no-store` + `noindex`, только авторизованному редактору |
| Заявки и сессии | никогда не кешируются |

`BASE_URL` задаётся окружением; localhost нигде не зашит.

## 11. Структура каталогов

Согласно ТЗ п. 6. Компоненты — в каталоге `Components` с заглавной `C`,
разделённые по доменам. Единый регистр путей во всех импортах (важно для Linux
на будущем VPS). Alias `@/*` настраивается на корень `frontend`.

Если генератор создаст `src/` — структура приводится к соглашению ТЗ без
пересоздания проекта.

## 12. Порядок реализации

Восемь этапов, каждый завершается проверяемым состоянием.

| # | Этап | Критерий завершения |
|---|---|---|
| 1 | `create-next-app`, git + `.gitignore`, зависимости, `.env` | `npm run build` проходит |
| 2 | Prisma-схема, миграции, индексы-инварианты | миграция применена к `events`, таблицы существуют |
| 3 | better-auth, роли, `create-admin` | вход работает, недостаточная роль отклоняется |
| 4 | CMS: страницы и шаблоны, дерево услуг, блог, категории, медиа, настройки, меню | записи создаются и сохраняются в БД |
| 5 | Публичная часть по референсу | страницы отдают контент из БД |
| 6 | Заявки, SEO, предпросмотр, редиректы, инвалидация | заявка в БД, 301 работает |
| 7 | Автопроверки ТЗ п. 12 | тесты зелёные |
| 8 | README, lint, typecheck, production build | ручной сквозной сценарий пройден |

**Git инициализируется до создания `.env`.** ТЗ п. 3 требует исключить секреты
из Git, а пароль базы уже известен. Файл, однажды попавший в коммит, удаляется
из истории болезненно — порядок здесь имеет значение.

## 13. Автоматические проверки

Реализуются семь сценариев ТЗ п. 12, каждый закрывает класс ошибок:

| Сценарий | Класс ошибок |
|---|---|
| Защищённая операция без сессии / с недостаточной ролью отклоняется | обход авторизации |
| Цикл в дереве услуг запрещён; перенос ветви сохраняет целостность и адреса | порча структуры данных |
| Неопубликованная запись недоступна публично | утечка черновика |
| Перенос/переименование родителя создаёт корректные редиректы потомков; неверный путь → 404 | битые адреса |
| Нарушение уникальности slug и конфликт системного URL отклоняются | коллизия маршрутов |
| Статья с несколькими категориями; удаление используемой категории запрещено | каскадная потеря данных |
| Валидная заявка сохраняется, невалидная отклоняется | потеря обращений клиентов |

## 14. Границы

Не входит в эту версию (согласно ТЗ п. 11): расписание исполнителей, склад
реквизита, бухгалтерия, онлайн-оплата, личный кабинет клиента, мультиязычность,
drag-and-drop конструктор страниц, версионирование редакций.

Результат — локально работающий проект. Публикация на production и изменение
инфраструктуры в задачу не входят (ТЗ п. 13).
