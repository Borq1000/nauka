# ВАУ! НАУКА

Сайт организатора праздников со встроенной CMS. Next.js (App Router) и PostgreSQL в одном приложении, без отдельного бэкенда.

## Версии

Требуется Node.js ≥ 20.9.0. Остальной стек зафиксирован в `package.json` — фактические установленные версии:

- Next.js 16.3.5, React 19.2.8, TypeScript 5
- Tailwind CSS 4
- Prisma 7.10.0 / `@prisma/client` 7.10.0
- better-auth 1.7.4
- Zod 4.6.4
- Vitest 5.0.0

## Запуск в разработке

Эти шаги доводят чистый клон до работающего входа в панель управления.

1. Скопировать `.env.example` в `.env` и заполнить реальными значениями (адрес базы данных, секрет подписи сессий и т.д.). Файл `.env` никогда не коммитится — он исключён из Git.
2. Установить зависимости:

   ```bash
   npm install
   ```

3. Сгенерировать клиент Prisma — обязательно после установки и перед первой сборкой:

   ```bash
   npx dotenv -e .env -- npx prisma generate
   ```

   Это ручной шаг, а не `postinstall`-хук: Prisma 7 не подхватывает `.env` сама, поэтому `prisma generate`, выполненный автоматически при `npm install` без уже экспортированных переменных окружения, падает с ошибкой и ломает установку на чистом клоне и в CI. Без этого шага сборка упадёт с `Cannot find module '@/generated/prisma/client'`.

4. Применить миграции к рабочей базе данных:

   ```bash
   npx dotenv -e .env -- npx prisma migrate deploy
   ```

   Без этого шага база остаётся пустой — ни одной таблицы, ни одного пользователя — и приложение не запустится. `migrate deploy` применяет только уже существующие в `prisma/migrations/` миграции, ничего не генерирует и не удаляет: это тот же самый недеструктивный способ, которым миграции применяются в проде.

   **Никогда не используйте** `prisma migrate reset` (удаляет данные) или `prisma db push` (обходит историю миграций) — оба запрещены для этого проекта.

   Если вносите изменения в `prisma/schema.prisma` и создаёте НОВУЮ миграцию, обычная команда — `prisma migrate dev`. Она требует права на создание временной shadow-базы (`CREATE DATABASE`). Если у роли PostgreSQL этого права нет (например, на управляемом хостинге), укажите заранее подготовленную shadow-базу через `shadowDatabaseUrl` в `prisma.config.ts` вместо того, чтобы просить у роли лишние права. `prisma migrate dev` в этом проекте также **не перегенерирует клиент автоматически** — после каждой новой миграции обязательно повторите шаг 3 (`prisma generate`).

5. Создать первого администратора — без этого войти в панель управления невозможно, публичной регистрации в проекте нет:

   ```bash
   npm run create-admin
   ```

   Интерактивная команда: спрашивает email и имя, затем дважды просит пароль (ввод скрыт, минимум 12 символов). Требует запуска напрямую в терминале (не через перенаправление ввода/вывода). Email автоматически приводится к нижнему регистру — уникальность email в базе не зависит от регистра.

6. Запустить сервер разработки:

   ```bash
   npm run dev
   ```

   Приложение поднимется на [http://localhost:7622](http://localhost:7622), вход в панель управления — на `/admin/login`.

## Тесты

```bash
npm test
```

Тесты работают с отдельной базой `events_test`, а НИКОГДА не с рабочей `events`: `tests/setup.ts` перед запуском перенаправляет `DATABASE_URL` на `DATABASE_URL_TEST` и отказывается работать, если `DATABASE_URL_TEST` не задан или совпадает с рабочим `DATABASE_URL`. `events_test` должна существовать и иметь применённые миграции — так же, как рабочая база (шаг 4 выше, только с `DATABASE_URL_TEST` вместо `DATABASE_URL`).

## Продакшен: обратный прокси обязан выставлять `X-Real-IP`

Рейт-лимитинг better-auth (`lib/auth.ts`) определяет клиента по заголовку `X-Real-IP`. Обратный прокси перед приложением **обязан полностью перезаписывать** этот заголовок реальным адресом клиента, а не пропускать значение от клиента как есть — иначе рейт-лимит либо делится на всех клиентов сразу (один и тот же общий "бакет" на путь), либо обходится полностью (клиент сам подставляет любое значение).

Для nginx:

```nginx
proxy_set_header X-Real-IP $remote_addr;
```

Приложение при этом не должно быть доступно напрямую в обход прокси — иначе тот же заголовок подделывает сам клиент.

Что происходит без этого:
- **Локальная разработка (прокси нет вообще).** Заголовок отсутствует, better-auth в dev/test возвращает фиксированный `127.0.0.1` — один общий "бакет" на все локальные запросы. Это безопасно: локально и так всегда один реальный клиент.
- **Продакшен, прокси не настроен (заголовок отсутствует).** better-auth не может определить IP, логирует предупреждение и использует один общий "бакет" на путь на ВСЕХ клиентов сразу — один клиент может исчерпать лимит для всех остальных, включая владелицу, которая пытается войти в собственную панель управления.
- **Продакшен, прокси настроен правильно.** Каждый клиент получает свой "бакет" по реальному IP — рейт-лимитинг работает как задумано, включая более строгое правило для `/sign-in/email` (10 секунд / 3 попытки).

**Приложение отказывается запускаться в продакшене без явного подтверждения.** Переменная окружения `TRUST_PROXY_SETS_CLIENT_IP=true` (см. `.env.example`) обязательна, когда `NODE_ENV=production` — она подтверждает человеком, что прокси настроен именно так, как описано выше. Без неё `lib/env.ts` бросает ошибку при старте с объяснением на русском. Выставляйте её только после того, как проверили конфигурацию прокси — сама переменная ничего не проверяет технически, это осознанное подтверждение, а не переключатель.
